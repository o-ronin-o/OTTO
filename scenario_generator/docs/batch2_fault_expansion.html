Batch 2 — Engine-Side Faults + New Signal Design

Design discussion for the second batch of fault types, plus an open question
about adding a new signal before implementing these faults.

1. Context — Where We Are

The fault framework currently implements one fault type: brake_pad_wear.

Its characteristics:

The infrastructure for adding more fault types is in place: registry, injector, labels, tests, and the evolution timeline builder. What remains is to expand the fault library.

The plan: add fault types in batches. Each batch targets a distinct region of the vehicle (engine, braking, steering, electrical). This document covers Batch 2 — engine-side faults.

2. Open Question — Add a New Signal First?

Before implementing Batch 2, consider adding a new signal to the pipeline.
A new signal could make these faults — and future ones — produce more interesting reflection in the observable data.

The current 8 signals are:

engine_rpm
throttle_position
coolant_temperature
brake_pressure
brake_pedal
wheel_speed
vehicle_speed
longitudinal_acceleration

These are all longitudinal signals — they describe the vehicle's forward motion and its engine/braking behavior. There is no lateral or rotational signal in the set.

Candidate new signals

Each candidate is evaluated on: (a) how much it enriches fault expression, (b) its cost to add, (c) whether it unlocks new fault types.

Signal Unit Unlocks fault types Cost
steering_angle deg Power steering failure, steering sensor drift, steering lock Moderate — needs scenario support (turns), a physics model for steering
lateral_acceleration m/s² Chassis/alignment faults, ESC-related faults Moderate — derives from steering + speed
yaw_rate deg/s Yaw stability faults, vehicle spin detection Moderate — derives from steering + speed
intake_air_temperature celsius Air intake faults, turbo/intercooler faults Low — similar to coolant, warmup-style behavior
mass_air_flow g/s MAF sensor faults, throttle/intake leaks Low — correlates with RPM × throttle
battery_voltage V Electrical faults, alternator faults, battery aging Low — mostly constant, easy to model
fuel_trim_short % Fuel system faults, injector faults, O2 sensor faults Low — correlates with throttle/RPM

Why this matters for Batch 2

Batch 2's three faults target the engine. Their effects currently manifest as:

  • throttle_sensor_gain_fault — engine delivers more/less power than commanded
  • engine_misfire — engine torque drops intermittently
  • coolant_sensor_drift — coolant reading drifts from reality

The first two affect the engine's output. Currently, the only way to observe that is via engine_rpm and longitudinal_acceleration. Both are already busy signals with their own dynamics.

The pitch: adding mass_air_flow (MAF) or intake_air_temperature (IAT) would give these engine faults a cleaner, more direct observable. A misfire shows up in MAF as a sharp dip. A throttle gain fault shows up in MAF as a scaled flow. And both signals are cheap to add.

Three options

Option A — Add no new signal now

Implement Batch 2 with the existing 8 signals. Effects show up in engine_rpm and longitudinal_acceleration, as with brake_pad_wear. Simpler, faster.

Option B — Add one signal first

Before Batch 2, add a single new signal. My recommendation: mass_air_flow. It's the most direct observable of engine behavior after RPM, and it interacts meaningfully with the throttle gain fault and misfire.

Option C — Add two signals

Add mass_air_flow and intake_air_temperature. Gives the engine faults two independent observables.

Decision requested

Which option do you prefer?

My recommendation: Option B. Add mass_air_flow first. It's a low-cost addition, it makes Batch 2's faults more diagnostically rich, and it unlocks future fault types (MAF sensor faults, intake leaks, turbo issues) that wouldn't otherwise be expressible.

If we add mass_air_flow first, the sequence becomes:

  1. Design + add mass_air_flow signal (with a physics relationship to RPM and throttle)
  2. Then proceed with Batch 2 as designed below
  3. Update Batch 2's faults to also affect mass_air_flow where physically appropriate

3. Batch 2 — Engine-Side Faults

Three faults covering sensor and mechanical categories, affecting the engine/powertrain:

Fault D — throttle_sensor_gain_fault

sensor drift

Physical story:The throttle position sensor's signal is scaled by a gain error. The driver commands 50% throttle, but the ECU reads 60% (or 40%). The engine delivers torque based on the misread value.
Pipeline behavior:effective_throttle = throttle × (1 + gain_error(t)), then engine_torque = effective_throttle × max_torque.
Diagnostic signature:Engine delivers more/less power than the pedal would predict. The throttle→acceleration relationship is broken.
Target signals:engine_rpm, longitudinal_acceleration (cascade)
Physics input:throttle_multiplier — a new array applied to throttle before engine torque calculation
Parameters:gain_error_final (e.g., +0.3), progression

Fault E — engine_misfire

mechanical dropout (intermittent)

Physical story:One or more cylinders misfire intermittently. Engine torque drops to zero for brief intervals (10–50 ms) at irregular points.
Pipeline behavior:misfire_mask[i] ∈ {0, 1}, then f_engine = f_engine_clean × misfire_mask[i].
Diagnostic signature:Irregular, sharp dips in engine_rpm and longitudinal_acceleration. Transient, not sustained.
Target signals:engine_rpm, longitudinal_acceleration (cascade)
Physics input:engine_force_multiplier — a binary array applied to f_engine
Parameters:misfire_probability (e.g., 0.15), burst_length (e.g., 3), seed

Fault F — coolant_sensor_drift

sensor drift

Physical story:The coolant temperature sensor ages or gets contaminated. Its reading drifts from the true temperature. The engine itself is physically fine.
Pipeline behavior:coolant_reading = coolant_true + offset(t), where offset(t) ramps from 0 to max_offset.
Diagnostic signature:Coolant reading departs from the expected warm-up curve. A pure sensor fault — no other signal is affected.
Target signals:coolant_temperature only
Physics input:signal_offset — a post-physics override dict
Parameters:max_offset (e.g., +15°C), progression

4. New Physics Inputs Required

To express these three faults, the SignalGenerator.generate(faults={...}) interface must accept three new parameters (in addition to the existing brake_force_multiplier):

Physics input Type Applied where
throttle_multiplier array in [0, ~2] multiplies throttle[i] in _compute_dynamics
engine_force_multiplier binary array {0, 1} multiplies f_engine contribution
signal_offset dict[signal_name, array] adds to signals in Phase 3 (post-physics)

Total after Batch 2: 4 physics inputs (including existing brake_force_multiplier).

5. Design Questions Requiring Approval

Q1 — Which fault first?

The three faults can be implemented in any order. The sequence affects which machinery gets built first.

Recommendation: Coolant → throttle → misfire. Simplest physics hook first (signal_offset), then more complex (throttle multiplier), then the most complex (intermittent faults with randomness).

Q2 — Is throttle_sensor_gain_fault a gain fault or an offset fault?

Gain = multiplicative scaling (scales with input). Offset = additive bias (constant).

Recommendation: Gain. The name says gain, and gain is more interesting (a bias would be a special case of the offset mechanism we already need for coolant).

Q3 — For engine_misfire, what exactly does "engine force" mean?

The engine force is f_engine = wheel_torque / wheel_radius. Misfire reduces torque production.

Recommendation: Use engine_force_multiplier as the physics input, applied directly to f_engine. Same effect as scaling torque, simpler to reason about.

Q4 — How to handle randomness in engine_misfire?

Misfire uses randomness to determine which timesteps misfire. Until now, the pipeline has been deterministic.

Options:

  • Option A — Injector-level seed (fixed globally)
  • Option B — Fault-declared seed (each fault declares its own seed)
  • Option C — Per-scenario seed
  • Option D — Fixed deterministic pattern (non-random)
Recommendation: Option B. The fault declaration carries a seed. Reproducible, per-fault controllable, no hidden state.

Q5 — Misfire mask: per-timestep or per-burst?

Real misfires happen in bursts (a few cycles), not independent single-frame events.

Options:

  • Option A — Independent per-timestep (Bernoulli at each frame)
  • Option B — Burst mode (runs of several misfires)
Recommendation: Option B. Realistic dips, more distinctive signature, but slightly more code.

Q6 — Coolant sensor drift: additive or multiplicative?

Coolant temperature starts at ~20°C and approaches ~90°C. A drift could be additive (+15°C) or multiplicative (×1.2).

Recommendation: Additive. Physically natural for temperature sensors. Multiplicative doesn't make sense across the full range.

Q7 — Should we add an injection_point field to the fault registry?

Sensor faults (coolant drift) should apply after all physics and relationships. Physical faults (brake pad wear) apply during physics. The distinction matters for how downstream signals see the effect.

Options:

  • Option A — Rely on the existing layer field (signal vs. frame) to imply injection point
  • Option B — Add a new field injection_point: physics | post_physics
Recommendation: Option B. The layer field describes whether the fault operates on signals or frames. injection_point describes when in the physics pipeline it applies. These are orthogonal.

Q8 — Composition rules for overlapping faults?

If two faults of the same type target the same signal or physics input, how do they compose?

Proposed rules per fault family:

  • Gain faults — multiply: (1+ε₁)·(1+ε₂)
  • Mask-based faults — union: mask₁ | mask₂
  • Offset faults — add: offset₁ + offset₂
Recommendation: Adopt these family-specific composition rules. Each fault's registry entry declares a composition_rule field.

6. Proposed Implementation Order

The recommended sequence, conditioned on the decision in Section 2:

If we add mass_air_flow first (recommended)

  1. Add mass_air_flow signal — registry, relationship, CAN mapping, tests
  2. Coolant sensor drift — the simplest fault to build (signal_offset hook)
  3. Throttle sensor gain fault — introduces throttle_multiplier hook
  4. Engine misfire — introduces randomness and mask-based composition

If we do not add a new signal

  1. Coolant sensor drift
  2. Throttle sensor gain fault
  3. Engine misfire

7. What Each Fault Type Will Deliver

For each fault, following the same pattern established with brake_pad_wear:

  1. Registry YAML — config/faults/<fault_id>.yaml
  2. Physics hook — one new parameter on SignalGenerator.generate(faults={...})
  3. Injector handler — a small function in fault_injector.py
  4. Tests — validation, injection, labels, physical plausibility (~8–12 tests)
  5. Seed scenario — a scenario demonstrating the fault
  6. Notebook cells — for the fault validation notebook
